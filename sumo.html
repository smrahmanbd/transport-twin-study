Camera twin

Putting a camera on SUMO

The fourth controller never reads SUMO’s ground truth. It sees the road only through a virtual camera on a corner pole at each junction, modelled on what a computer-vision detector delivers in practice.

What the virtual camera does

  • Field of view: 110 m around the pole, all approaches.
  • Missed detections: 98% detection probability close up, falling to 80% at the edge of range.
  • Occlusion: a car hidden behind a nearer car on the same line of sight is not seen.
  • Noise: about 1 m position error per axis; speed comes from a tracker comparing noisy positions.
  • Map matching: the camera knows only x and y, so it must assign each detection to a lane itself.

Implementation steps · part 1

Build this twin in SUMO

About two hours on a laptop. Commands assume Python 3.9 or newer. Every file named here is in the sumo folder.

  1. Install SUMO and its Python tools

    pip install eclipse-sumo traci sumolib rtree
python -c "import sumo; print(sumo.SUMO_HOME)"     # set SUMO_HOME to this path

    On Windows you can also use the installer from eclipse.dev/sumo, which includes sumo-gui and netedit.

  2. Describe the road and build the network

    Nodes and edges are plain XML. netconvert turns them into a SUMO network with signal plans: one with fixed timing, one with SUMO’s actuated control.

    netconvert -n corridor.nod.xml -e corridor.edg.xml -o corridor_fixed.net.xml \
  --tls.default-type static --tls.cycle.time 90 --no-turnarounds true --tls.left-green.time 0
netconvert -n corridor.nod.xml -e corridor.edg.xml -o corridor_actuated.net.xml \
  --tls.default-type actuated --tls.cycle.time 90 --no-turnarounds true --tls.left-green.time 0

  3. Write the demand

    Twelve flows with a 20-minute peak, at three levels. Edit FLOWS to change volumes.

    python make_routes.py      # routes_low / routes_medium / routes_high .rou.xml

  4. Add the sensors

    Lane-area detectors (E2) cover the last 80 m of each approach; induction loops (E1) count every 5 minutes. The cameras are drawn for sumo-gui.

    python make_detectors.py corridor_fixed.net.xml   # detectors.add.xml
python camera_sensor.py                            # cameras.add.xml

  5. Run the baseline and watch it

    python run_scenario.py --controller fixed --demand medium
sumo-gui -c corridor.sumocfg                      # look around; the yellow circles are the cameras

  6. Connect the twin through TraCI

    The loop that makes it a twin: every simulated second, read the state, decide, write the decision back.

    traci.start(cmd)
twin = TwinController(source="detectors")
while traci.simulation.getMinExpectedNumber() > 0:
    traci.simulationStep()                 # the "physical" road moves one second
    twin.step(traci.simulation.getTime())  # sense → estimate → decide → act
traci.close()
    python run_scenario.py --controller twin --demand medium --gui

  7. Swap perfect sensors for cameras

    Same twin, but its state comes only from CameraSensor.detect(). Compare the two runs to see what imperfect sensing costs.

    python run_scenario.py --controller twin_camera --demand medium

  8. Calibrate against counts

    python calibrate_geh.py    # GEH before and after rescaling demand per entry

  9. Compare everything and export for the web

    python export_web.py       # 12 runs; writes ../data/*.json used by this page
Implementation steps · part 2

From SUMO to a real camera twin

The SUMO version proves the logic. A field deployment keeps the same loop and replaces each simulated piece with a real one.

  1. Agree the use case and the rules

    One junction or corridor, one decision (signal timing), one owner, success measures (delay, stops, pedestrian wait), and a safety case: minimum and maximum greens, fixed yellow and all-red, and a fallback plan the controller reverts to.

  2. Install and survey the cameras

    Pole height 8 to 12 m, covering every approach for at least 80 to 110 m. Record each camera’s position and survey four or more ground points visible in the image so pixels can be mapped to road coordinates. Run a privacy impact assessment and process video at the edge so no images leave the pole.

  3. Detect and track vehicles

    Run an object detector (for example a YOLO model) and a multi-object tracker (for example ByteTrack) on an edge computer. Output per frame: track id, class, bounding box, confidence.

  4. Turn pixels into lanes

    A homography maps the bottom-centre of each box to road coordinates; snap to lanes with the same map matching used in camera_sensor.py.

    import cv2, numpy as np
H, _ = cv2.findHomography(np.float32(pixel_pts), np.float32(road_pts))   # from the survey
def to_road(box):                     # box = (x1, y1, x2, y2) in pixels
    u, v = (box[0] + box[2]) / 2, box[3]          # bottom-centre touches the road
    p = H @ np.array([u, v, 1.0]); return p[0] / p[2], p[1] / p[2]

  5. Stream detections to the twin

    Publish compact messages over MQTT every 0.5 to 1 s. Keep timestamps from one synchronised clock (NTP or PTP).

    msg = {"cam": "cam_J2", "t": 1729782000.5,
       "dets": [{"track": 418, "x": 698.2, "y": 251.0, "speed": 0.4, "lane": "N2_J2_0"}]}
client.publish("corridor/cameras/J2", json.dumps(msg))

  6. Keep the simulation in step with the street

    The SUMO model becomes the twin’s state. Insert or move tracked vehicles so queues match what the cameras see, and recalibrate demand from counts every 15 minutes.

    for d in detections:                          # inside the twin's update loop
    vid = f"cam{d['track']}"
    if vid not in traci.vehicle.getIDList():
        traci.vehicle.add(vid, routeID="", typeID="car")
    traci.vehicle.moveToXY(vid, "", -1, d["x"], d["y"], keepRoute=2)

  7. Test decisions in the twin before using them

    Every few seconds, copy the current state into a short look-ahead run (30 to 120 s) for each candidate timing and pick the one with the least delay. The rule-based controller in twin_controller.py is the simple starting point.

  8. Act through a safety shell

    Send only “extend green” or “end green now” requests to the signal controller (for example through NTCIP 1202 objects or the vendor’s API). The controller hardware keeps enforcing minimums, yellows and conflict monitoring, and returns to its normal plan if messages stop.

  9. Run in shadow mode first

    For two to four weeks the twin only recommends. Log its advice next to what the signal actually did, check camera detection rates against manual counts, and fix the failure cases.

  10. Close the loop and keep measuring

    Switch to control on agreed hours, compare with matched days, and track detection rate, latency, delay and safety conflicts. Recalibrate after road works, seasonal changes or camera moves.
